**Vercube 1.5 is out.** The headline is [`@vercube/client`](https://www.npmjs.com/package/@vercube/client): a `fetch` wrapper whose types come from your controllers, so the frontend and the API can no longer disagree without the compiler saying so. Around it, errors you declare on a route reach the caller as a typed union, health probes make a rolling deploy drop nothing, `create-vercube` can now assemble a project from modules, and about thirty fixes close gaps on the request path.

## A client typed by your controllers

The usual way to keep a frontend honest about an API is to describe the API twice: once in the controllers and once in a hand-written client, an OpenAPI generator or a shared types package. The second copy drifts. `@vercube/client` has no second copy. The response is what the handler returns, the body is what its `@Body()` parameter accepts, and the path parameters are the `:segments` of the route.

```ts [src/api.ts]
import { createClient } from '@vercube/client';
import type { VercubeRoutes } from '../.vercube/routes.js';

const api = createClient<VercubeRoutes>({ baseURL: 'http://localhost:3000' });

const user = await api.get('/users/:id', { params: { id: '42' } });
//    ^? { id: string; name: string; createdAt: string }

await api.post('/users', { body: { name: 'Ada' } });
```

Rename a field in the handler and every call that no longer fits stops compiling. The client has no dependencies, weighs about 1.5 kB minified and gzipped, and runs wherever `fetch` does.

The part I spent the most time on is `.vercube/routes.d.ts`, the file that tells the client which routes exist. It is generated from the running application, so it lists exactly what the router serves, including controllers mounted with `setControllerPath()` and routes added by plugins. And it holds no types of its own:

```ts [.vercube/routes.d.ts]
export interface VercubeRoutes {
  'GET /users/:id': RouteDef<UserController, 'getUser', { param: { id: 0 } }>;
  'POST /users': RouteDef<UserController, 'create', { body: 0 }>;
}
```

Each entry names a controller, a method and the position of each parameter decorator, and the compiler works out the rest from the controller itself. That is why the file only changes when a route is added, removed or moved, and why a pull request shows an API change as a small diff you can commit and review. It is kept current by `vercube dev` on every restart, by `vercube build`, and by the Vite plugin on every reload.

`app.client` in [`@vercube/testing`](/docs/modules/testing/overview) is the same client pointed at the app in memory, so tests get the same types:

```ts
await using app = await createTestApp<VercubeRoutes>({ controllers: [UserController] });

const user = await app.client.post('/users', { body: { name: 'Ada' } });
```

## Errors that survive the trip

A typed response is half of the contract. The other half is what the route answers when it does not succeed, and until now that was `catch (e: unknown)`. `@Throws()` declares it on the route:

```ts [src/Controllers/UserController.ts]
@Put('/:id/email')
@Throws(NotFoundError, ConflictError)
public async changeEmail(@Param('id') id: string, @Body() body: { email: string }): Promise<User> {
  return this.users.changeEmail(id, body.email);
}
```

The declaration lands in the route map, and `api.safe` uses it. It has the same calls as `api`, but resolves to `{ data, error, response }` instead of rejecting, and `error` is a union with one member per declared status:

```ts
const res = await api.safe.put('/users/:id/email', { params: { id }, body: { email } });

if (res.error) {
  switch (res.error.status) {
    case 400:
      return showIssues(res.error.body.errors ?? []); // validation issues
    case 404:
      return null;
    case 409:
      return pickAnother(res.error.body.existingId); // the ConflictError's own field
    default:
      throw res.error;
  }
}

res.data; // User
```

A route behind `@Auth()` gets `401` and `403` in the union without you declaring them, and `500` never appears, because a server fault is not something the caller handles by branching. The same declarations feed `@vercube/schema`, so the OpenAPI document lists the error responses a route can give.

I kept `api.safe` as a namespace rather than a `{ throw: false }` option on purpose. An option would make the return type depend on a runtime flag, and the two shapes are different enough that the type should say which one you hold.

## Health checks and rolling deploys

One option gives the application the probes an orchestrator expects:

```ts [vercube.config.ts]
export default defineConfig({
  health: true,
});
```

```bash
curl -s localhost:3000/_health/live     # {"status":"ok"}
curl -s localhost:3000/_health/ready    # {"status":"ok","checks":{"queue:default":{"status":"ok"}}}
curl -s localhost:3000/_health/startup   # {"status":"ok"}
```

Liveness checks nothing, on purpose. A database outage should take a pod out of the load balancer through readiness, not make Kubernetes restart a healthy process in a loop. The modules register their own readiness checks: the queue pings its broker, the scheduler its store, and the S3 storage does a `HeadBucket`. Your own go through `app.health.register()` with a timeout and a `critical` flag, and a non-critical one is reported without failing readiness.

The second half is what happens on `SIGTERM`. Kubernetes starts removing the pod from the endpoints at the same moment it sends the signal, and that removal takes a few seconds to reach every node. A server that stops accepting connections immediately refuses requests during exactly that window. With `health` on, readiness answers `503` first, the server keeps serving for `shutdown.drainDelay` (5 seconds by default), and only then stops accepting connections and waits for requests in flight. Turning on `health` also turns on `shutdown.handleSignals`, so a deploy is zero-downtime without any further setup.

By default the readiness body names each check and never an error message, which could reveal a host name or a credential problem. The full report goes to requests that carry `health.token`. The probes also skip application-wide middlewares and telemetry, so a global auth middleware never locks the orchestrator out and the Requests panel in devtools is not buried under one entry per probe.

## A project generator with modules

`create-vercube` used to download one template. It now assembles a project from the modules you pick:

```bash
pnpm create vercube my-app --template fullstack-vue --modules schema,auth,queue,testing --queue rabbitmq --yes
```

Every module is a recipe: a plugin goes into `vercube.config.ts`, a binding into your container, a sample route and its test next to the starter controller, and the service it needs, such as Redis or RabbitMQ, into `docker-compose.yml`. Code is edited through its syntax tree, and every recipe checks what is already there, so running it twice changes nothing and a file you edited is never overwritten.

The same recipes work on an existing project:

```bash
pnpm vercube add queue --queue rabbitmq
pnpm vercube add cache,ws --yes
```

There are two templates. `api` is the API alone. `fullstack-vue` is a workspace with the API and a Vue app on Vite, where one `dev` at the root starts both, Vite proxies `/api` to the API, and the web app calls it through `@vercube/client`, typed by the controllers next to it. Deploy targets cover Node, AWS Lambda and Azure Functions. Without a terminal, a missing answer fails with every flag still needed instead of waiting for input, which makes it usable from CI and from an agent.

A package can ship a recipe of its own, and `vercube add @acme/vercube-search` applies it.

Read more: **[Project generator](/docs/getting-started/project-generator)** · **[Writing a recipe](/docs/advanced/writing-a-recipe)**.


## Devtools, redesigned

`@vercube/devtools` was rebuilt to match the new look of this site. The panels are the same ones, laid out as an instrument panel rather than a set of tables, and a few rough edges went with the redesign: value previews no longer mark a shared reference as circular, only a real cycle. Devtools state-changing endpoints now also refuse cross-site requests.


## A security pass over the request path

After 1.4 I went back over the places where the framework meets the outside world and read them as an attacker would. Most of what I found was small and none of it was a crash, which is the kind that survives longest. The ones worth knowing about:

- **Error responses do not carry the error.** An unexpected error no longer returns its message or `cause` to the caller, outside development.
- **The OpenAPI document is not served in production.** `/_schema` lists every route, parameter and security scheme of your API, so it is off when `production: true`. Turn it back on with `enabled: true`, and put it behind `token` and a `path` of your choosing. The Scalar bundle it loads is pinned with an integrity hash and served with a `Content-Security-Policy`.
- **WebSocket upgrades check `Origin`.** A browser sends cookies with the handshake even when another site opens the socket, and CORS does not cover it, so a cookie-authenticated gateway could be driven by a malicious page. Only same-origin browsers are accepted by default, and `allowedOrigins` takes a list or a function. A connection guard is also looked up with the normalized namespace now, so `/chat/` and `/chat` no longer differ.
- **Static files** ignore dotfiles, refuse symlinks that leave the static directory, and each directory is served only under its own prefix.
- **Telemetry redacts by name.** Headers and keys named like credentials (`authorization`, `cookie`, `session`, `jwt`) are redacted in captured headers, JSON and urlencoded bodies.
- **Auth fails closed.** A `validate()` that returns something unexpected is a rejection, not a pass.
- **Generated code is escaped.** Import paths containing quotes or `$` sequences, and template literal route paths, no longer produce broken or surprising output from `@vercube/scan`.
- **Module edges.** The S3 readiness check fails on `403`, the queue waits out delays longer than the timer limit, a RabbitMQ channel closed mid-message cannot escape the handler, and the S3 `clear` is batched.

One small change in the same spirit: a handler that returns `undefined` now answers `204 No Content` instead of a `200` with an empty body.

And one addition from the auth work. `validate()` can now return `{ user }`, and `@User()` uses it instead of asking the provider a second time. A route with both `@Auth()` and `@User()` used to resolve the user twice, typically a session lookup or a database query each.

```ts
public async validate(): Promise<AuthTypes.ValidationResult<Account>> {
  const account = await this.accounts.bySession(this.session());

  return account ? { user: account } : { error: 'No session' };
}
```

A provider that returns `string | null` keeps working unchanged.


## Upgrade

Every `@vercube/*` package is released together and has to be on the same version, so update all of them at once:

```bash
pnpm up "@vercube/*" --latest
```

Then add the new package at the same version:

```bash
pnpm add @vercube/client@1.5.0
```

Most applications upgrade without touching anything. A few behaviours changed on purpose, and they are worth a search through your code:

- **`/_schema` is not served when `production: true`.** If you publish the reference from production, set `enabled: true` and a `token`.
- **A handler that returns `undefined` answers `204`**, not `200`.
- **Unexpected errors no longer echo their message** to the caller outside development. Look in your logs, or in devtools, instead of the response body.
- **WebSocket upgrades from another origin are rejected with `403`.** Requests without an `Origin` header (server-to-server clients, CLI tools, native apps) are not affected. If a frontend on another origin connects, list it in `allowedOrigins`, and behind a proxy that rewrites `Host` forward the original with `X-Forwarded-Host`.
- **`health` changes two defaults when it is on:** `shutdown.drainDelay` becomes 5000 and `shutdown.handleSignals` becomes `true`. Setting either explicitly wins. Keep `terminationGracePeriodSeconds` above `drainDelay + timeout`.

The full list of changes is in the [changelog](https://vercube.dev/changelog).
