## A client typed by your controllers

[`@vercube/client`](https://www.npmjs.com/package/@vercube/client) is a `fetch` wrapper with no second description of your API to keep in sync. The response is what the handler returns, the body is what `@Body()` accepts, and the path parameters are the `:segments` of the route.

```ts
const api = createClient<VercubeRoutes>({ baseURL: 'http://localhost:3000' });

const user = await api.get('/users/:id', { params: { id: '42' } });
//    ^? { id: string; name: string; createdAt: string }
```

Rename a field in a handler and every call that no longer fits stops compiling. The route map it relies on is generated from the running app by `vercube dev`, `vercube build` and the Vite plugin, and holds no types of its own, so it is small enough to commit and review. About 1.5 kB gzipped, and it also powers `app.client` in `@vercube/testing`.

Read more: **[Client](/docs/modules/client/overview)**.


## Errors that survive the trip

Declare what a route can answer with, and the caller gets it as a union instead of `catch (e: unknown)`:

```ts
@Put('/:id/email')
@Throws(NotFoundError, ConflictError)
public changeEmail(@Param('id') id: string, @Body() body: { email: string }) {}
```

```ts
const res = await api.safe.put('/users/:id/email', { params: { id }, body });

if (res.error?.status === 409) {
  pickAnother(res.error.body.existingId); // the ConflictError's own field
}
```

The same declarations land in the OpenAPI document that `@vercube/schema` generates.

Read more: **[Typed errors](/docs/modules/client/requests#typed-errors)**.


## Health checks and rolling deploys

```ts [vercube.config.ts]
export default defineConfig({ health: true });
```

That gives you `/_health/live`, `/ready` and `/startup`, readiness checks registered by the queue, the scheduler and S3 storage, and a shutdown that answers `503` first and keeps serving for a few seconds, so a Kubernetes rolling update drops no requests.

Read more: **[Health checks](/docs/core-features/health)**.


## A project generator with modules

```bash
pnpm create vercube my-app --template fullstack-vue --modules schema,auth,queue,testing
pnpm vercube add cache,ws
```

`create-vercube` now assembles a project from modules, each one a recipe that edits your config and container, adds a sample route and its test, and brings the Redis or RabbitMQ it needs. `vercube add` applies the same recipes to a project that already exists, and running one twice changes nothing. The new `fullstack-vue` template is an API and a Vue app in one workspace, wired together through the typed client.

Read more: **[Project generator](/docs/getting-started/project-generator)** · **[Writing a recipe](/docs/advanced/writing-a-recipe)**.


## Security pass

After 1.4 I went back over the places where the framework meets the outside world. None of it was a crash, and most of it is now simply handled. The ones you are most likely to notice:

- Unexpected errors no longer echo their message or `cause` outside development.
- `/_schema` is not served in production by default. Turn it on with `enabled: true`, behind a `token`.
- WebSocket upgrades check `Origin`, and `allowedOrigins` lets a frontend on another origin in.
- Static files ignore dotfiles and refuse symlinks that leave the directory.
- Telemetry redacts credential-named headers and body keys.
- Auth fails closed on an invalid `validate()` result, and `validate()` can return `{ user }` so `@User()` does not load it a second time.

The rest, around thirty fixes in all, is in the [changelog](https://vercube.dev/changelog). Devtools also got the new look, and its state-changing endpoints now refuse cross-site requests.


## Upgrade

Every `@vercube/*` package is released together and has to be on the same version:

```bash
pnpm up "@vercube/*" --latest
pnpm add @vercube/client@1.5.0
```

Most applications upgrade without touching anything. A few behaviours changed on purpose:

- **`/_schema` is not served when `production: true`.** Set `enabled: true` and a `token` to keep it.
- **A handler that returns `undefined` answers `204`**, not `200`.
- **Unexpected errors no longer echo their message** to the caller outside development. Look in your logs or in devtools.
- **WebSocket upgrades from another origin get `403`.** Requests without an `Origin` header are not affected. List a frontend on another origin in `allowedOrigins`.
- **`health` changes two defaults when on:** `shutdown.drainDelay` becomes 5000 and `shutdown.handleSignals` becomes `true`. Setting either explicitly wins.
