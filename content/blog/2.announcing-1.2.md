**Vercube 1.2 is out.** Three things carry this release: a devtools inspector served by your own application, a performance pass that changed what a request costs, and a cache decorator that makes any method cacheable.

## Devtools

[`@vercube/devtools`](https://www.npmjs.com/package/@vercube/devtools) mounts an inspector inside the app you are already running. Open `/_devtools` and you see the dependency injection container, the route table, request waterfalls, logs, storage, resolved config, a bootstrap profile and an audit. It is one self-contained HTML page served by the app itself: no separate process, no outbound traffic, nothing phoning home.

<video class="w-full rounded-lg border border-default" src="/video/devtools/overview.mp4" controls muted loop playsinline preload="metadata"></video>

The panel I use most is **Requests**. Every request is recorded with the status the client actually observed, and opening one gives a waterfall: a span per middleware, one for the handler, and the framework time left over for routing, argument resolution and serialization. The log lines written during that request, the bodies and the headers sit right underneath, so "why is this endpoint slow" usually takes one click rather than a bisect through `console.log`.

The rest of the panels answer the questions that are normally hard to ask a running server. **Graph** draws the container, marks bindings nothing ever resolved, rings dependency cycles and flags an `@Inject` of a key nothing binds before it throws. **Routes** shows the middleware chain in execution order with phases and priorities, and marks arguments that reach a handler unvalidated. **Bootstrap** is a flamegraph of container construction ranked by self time, which is where a constructor doing I/O at boot finally becomes visible. **Audit** turns all of that into findings scored 0 to 100.

Getting it is two lines:

```ts [vercube.config.ts]
import { defineConfig } from '@vercube/core';
import { DevtoolsPlugin } from '@vercube/devtools';

export default defineConfig({
  plugins: [DevtoolsPlugin],
});
```

Devtools are development-only by default. In production the plugin refuses to mount without an access token, credential-bearing headers and config values are redacted, and the devtools mount is deliberately detached from your global middlewares so an auth middleware cannot lock you out of your own inspector.

Read more: **[Devtools overview](/docs/modules/devtools/overview)** · **[PR #1141](https://github.com/vercube/vercube/pull/1141)**.

## A much faster request

Vercube was doing work on every request that most routes did not need: validation middleware with no schema attached, cloning the body, wrapping every call in `AsyncLocalStorage`, building a `URL` object just to read a pathname, walking the router trie for paths that never change.

1.2 adds a fast path for simple routes and stops charging you for features you did not turn on. `@Body()` and `@QueryParam()` only attach validation middleware when you pass a schema. The body is cloned only when something actually reads it twice. Static routes are cached. Pathname parsing on the hot path no longer goes through `new URL()`. And the per-request async context became optional:

```ts [vercube.config.ts]
export default defineConfig({
  requestContext: false, // skip the async context frame if you never inject RequestContext
});
```

Measured against 1.1.7:

| Runtime | Overall throughput          | JSON responses                  |
| ------- | --------------------------- | ------------------------------- |
| Bun     | **+58%** (56.8k to 89.9k RPS) | **6.3x** (17.5k to 110.6k RPS) |
| Node    | **+30%** (52.4k to 68.0k RPS) | **2.9x** (29.6k to 86.2k RPS)  |
| Deno    | +2%                         | roughly flat                    |

On Node, resident memory after a load run also drops from about 624 MB to about 297 MB.

The honest footnotes: plain `GET` routes move much less, roughly 2% to 20% depending on runtime, because they were never paying most of that cost. Startup is a few milliseconds slower and the Bun bundle grew from 237 KB to 538 KB, because a fast path is more code, not less. Deno barely moved. As always, these are benchmark numbers from one suite; your application is the only benchmark that matters.

Read more: **[PR #1139](https://github.com/vercube/vercube/pull/1139)**.

## The cache decorator

[`@vercube/cache`](https://www.npmjs.com/package/@vercube/cache) turns any method into a cached one with a single decorator. It is built on [ocache](https://ocache.unjs.io), the standalone extraction of Nitro's cache layer, so time-based expiration, stale-while-revalidate, deduplication of concurrent calls and invalidation when your code changes all come for free. Entries live in a regular [Storage](/docs/modules/storage/overview) mount, which means memory, S3 or any other driver backs your cache without a line of glue code.

::code-group

```ts [src/container.ts]
import { CacheManager } from '@vercube/cache';
import { StorageManager } from '@vercube/storage';
import { MemoryStorage } from '@vercube/storage/drivers/MemoryStorage';

export async function setupContainer(container: Container): Promise<void> {
  container.bind(StorageManager);
  container.bind(CacheManager);

  await container.get(StorageManager).mount({ name: 'cache', storage: MemoryStorage });
  container.get(CacheManager).configure({ storage: 'cache', maxAge: 60 });
}
```

```ts [src/services/UsersService.ts]
import { Cache } from '@vercube/cache';
import type { CacheTypes } from '@vercube/cache';

export class UsersService {
  @Cache({ maxAge: 300, swr: true, staleMaxAge: 900 })
  public async getUser(id: string): Promise<User> {
    return this.database.findUser(id);
  }

  public async updateUser(id: string, patch: Partial<User>): Promise<User> {
    const user = await this.database.updateUser(id, patch);

    // drop the cached entry for this user only
    await (this.getUser as CacheTypes.CachedMethod<[string], User>).invalidate(id);

    return user;
  }
}
```

::

The first call hits the database, the rest are served from storage, and simultaneous calls for the same `id` share a single round trip. A controller action is just a method, so decorating one caches the response keyed by its resolved route parameters.

Read more: **[Cache module overview](/docs/modules/cache/overview)** · **[PR #1098](https://github.com/vercube/vercube/pull/1098)**.

## Upgrade

```bash
pnpm add @vercube/core@latest
pnpm add -D @vercube/devtools
pnpm add @vercube/cache @vercube/storage
```

Nothing in this release breaks an existing 1.x application. `requestContext` stays on by default, validation keeps running wherever a schema is attached, and devtools do nothing until you register the plugin.

The full list of changes is in the [changelog](https://vercube.dev/changelog).
